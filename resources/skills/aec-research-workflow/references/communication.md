# Communication deliverables

Nearly every research task ends with a message, an email or a script for a supervisor, PI, collaborator or student. These are deliverables in their own right.

## Messages to the supervisor or group (WhatsApp style)

- Short, human and copyable: put the message in a **code block** so it can be pasted as is.
- Respect length caps exactly when given ("in 100 words", "30 words", "one line").
- State facts plainly; do not apologise ("dont apologise just state it").
- If it is long, split it into two blobs.
- Pair the message with the files to attach and their absolute paths. A typical package: one zip in a `Share_WhatsApp/` folder plus the message text.
- When a decision is needed, end with the specific decisions as a short numbered list.

## Emails

- Short (about 100 to 150 words), with a list of what to attach and where each file is.
- **Draft only.** Never send email from a session; the researcher sends it.
- No em dashes; polite, plain wording to the PI and co-authors.

## Explanations and scripts

- "Explain it to me like I'm five", then "now like I'm in college": layered explanations of the same result.
- Call scripts for talking a supervisor through changes, and short spoken-style scripts for presentations to specialists.
- Concept one-pagers and explainer images for collaborators outside the field.

## Proposals to run something

Before an expensive run, send a proposal that states what will run, why, the compute time from a pilot, and what decision is needed. Run only after approval.

## Public posts

LinkedIn posts after publication: plain, specific, crediting co-authors and the venue, no hype words.

## Always say where things are

- Give absolute paths, and say which file is current and which zip to attach.
- Name files so the version is obvious (`_v<N>_<date>`).

## Administrative documents

- Use only facts the researcher has confirmed; mark anything only the PI can confirm.
- Give direct "what do I fill in" lists in the requester's format.
